# Diagnose behavior and report findings

The deliverable diagnoses the **pinned SDD Manager plugin** from real consumer behavior, including assisted and failed first attempts. Deterministic harness checks establish observable facts; independent assessment establishes scope/ownership/workflow behavior. Do not convert missing facilities into invented defects or a consumer's eventual pass into proof that its initial attempt succeeded.

## Final report

Maintain `DIAGNOSTIC-REPORT.md` progressively under the run campaign and finish it with four explicit answers first:

1. **Demonstrated behavior:** which plugin capabilities/source-loading or installed-client paths actually ran, with exact pinned identity and coverage limits.
2. **Observed issues:** case/attempt outcomes, assistance, confidence and unresolved investigations, including environment/checker/input problems.
3. **Actions taken:** test project/harness/input clarifications, consumer repairs, external restorations and any separately authorized plugin change. A campaign itself does not repair its tested source.
4. **Proposed plugin changes:** bounded proposals with evidence/recheck, or the explicit conclusion below.

If no confirmed defect is established, state: **“No confirmed SDD Manager defects were identified; no test-derived plugin change is proposed.”** Separately list concrete unresolved investigations. Missing installed-client execution or other facilities are coverage gaps, not Passed cases or invented defects. This statement does not erase assisted attempts or unresolved instruction weakness.

Then include source full SHA/manifest (or dirty snapshot), resolved scope/profile/runtime, run/repository/branch identity, a reconciled A-001–A-027 table, attempts and initial/eventual outcomes, source/evidence links, product commit/merge/publication/hosted state, retained pending work, verified stop checkpoint and exact next authorized action. Distinguish native transcripts from observations, injected failures from provider failures, and consumer actions from fixture scripts. Use real runtime identities/links; never pre-fill historical issue numbers/SHAs/results.

## Finding record

Assign stable finding ID and record exact source/input/case/attempt, expected versus observed behavior, sanitized evidence links, first-attempt result, intervention/retry, likely cause/confidence, reproduction, bounded proposal and objective recheck. Preserve original input/checker versions; do not silently change expectations to match output. Quote only necessary non-secret instruction fragments and retain their source/hash.

| Attribution | Evidence needed before conclusion |
| --- | --- |
| Input | Exact supplied brief/authorization and ambiguity/omission; distinguish omitted requirement from present requirement the consumer missed |
| Consumer | Actual decision/actions against supplied input and loaded guidance; identify context/isolation/skill-loading limits |
| Checker | Independent literal contract and sensitivity result show a false positive/negative, missing collection or incorrect state interpretation |
| Environment | Observed runtime/client/transport/provider failure, actual missing facility and retained local/unknown effects |
| Plugin | Reproducible missing, contradictory or ineffective instruction at pinned identity; exact loaded entries, valid input and plausible alternatives checked |

Confidence may be confirmed, likely or unresolved; explain the discriminating evidence. Input/consumer attribution requires evidence and can coexist with instruction weakness. A successful retry alone cannot identify cause. An unrelated baseline failure requires actual independent baseline execution; zero-selected-test success is inadequate verification. Do not let verify repair task/source state itself merely to pass a checker.

## Repair proposals and recheck

A proposal names affected package paths, observed trigger, smallest instruction change and its expected behavior, compatibility/scope risks, and an objective rerun that fails without the fix and succeeds with it. The current campaign freezes tested source. Any accepted repair uses a separate change and **new full SHA/hash identity**, retaining old failures; it does not retroactively pass the old source. Harness/input repairs may continue the campaign with assistance disclosed and original versions retained. Never treat a new acceptance bundle as a requirement to add test transaction machinery to ordinary product workflows.

A-027 independently reconciles all outcomes and evidence/publication. Report outstanding publication/unknown hosted effects precisely, with no duplicate replay. Final coverage says what was demonstrated, what remains blocked/not run and why; a local-only subset is not full acceptance.
