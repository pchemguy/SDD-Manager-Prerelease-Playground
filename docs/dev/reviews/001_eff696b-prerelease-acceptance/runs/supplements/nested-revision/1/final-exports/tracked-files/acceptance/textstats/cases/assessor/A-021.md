Dispatch selected incorporation and observe first real selected-owner edit or source move, while another required selected link/list transfer remains pending. Do not create the partial transfer as setup.

## Deterministic partial-transfer setup

Bind actual selected owner/link operations from the consumer's authorized work. Use the caller-owned cooperative control in [TRIAL-CONTROLS](../../TRIAL-CONTROLS.md) between operations, with selected paths still pending named in `pending_paths`. Do not race polling, stop only after all transfers, or substitute a pending QC report for pending task/source ownership work. Preserve actual index, task/source bytes, links and feature identity at the gate.

The operations must be those selected and performed by the actual consumer. Coordinator-authored successful edits or support-fixture mutations do not count as consumer transfer. A separate fresh context resumes the same held state; native kill is an optional extension, not a prerequisite for required cooperative recovery. If the selected operation is atomic, choose a genuinely separable multi-owner request within authorized scope before dispatch; do not invent a partial move afterward.

- Fresh continuation retains feature identity/actual paths, consults both lists, establishes sole selected ownership/links, preserves still-needed sources and history; no duplicate archive.

Assess both interrupted and resumed attempts; a final clean state alone cannot satisfy this case.
