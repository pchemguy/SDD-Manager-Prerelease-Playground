# Execute the plugin test campaign

The coordinator selects catalog cases within resolved scope and assesses **plugin behavior** through real consumers. Product phase numbers/task IDs are derived by the consumer; P0–P5 organize this test, not product work. [Catalog](cases/catalog.json) dependencies, operating modes and triggers control eligibility. A requested subset does not authorize silently implementing missing prerequisites: reuse verified actual checkpoints or report Blocked. Scope `{}` is full; nonempty phase/case filters select matching entries, with both filters intersecting when both are supplied. Dependencies outside a bounded selection need an existing assessed checkpoint or explicit broader authorization.

## Phase gates

| Phase | Coordinator action and boundary |
| --- | --- |
| P0 — Resolve/initialize | Resolve repository/access/scope and fresh/resume; pin source/runtime/harness, reserve run/evidence identity, publish resolved inputs/harness. No product implementation. |
| P1 — Prepare/select | A-001 prepares ordinary product governing documents/tasks; A-002 is selection only; A-003 establishes real GitHub tracking. Independent preparation/selection/projection assessment before implementation. |
| P2 — Baseline | A-004 first task, A-005 usable milestone, A-006 complete Phase 1 failures/docs/distribution/integration. Record each actual task commit/push and final working/prospective/committed merge checks. |
| P3 — Increment/feature/steer | A-007 JSON, A-008 feature preparation, A-009 SPEC-only incorporation, A-010 feature implementation/selected ownership/archive, A-011 assessment-only subtraction, A-012 commanded removal, A-013 explicit stdin continuation/final phase integration. Publish assessed prerequisites between cases. |
| P4 — Failures/interruptions | A-014–A-026 use isolated forks from actual reached prerequisite checkpoints. Run when dependencies exist, including between earlier positive cases where necessary; do not fabricate finished prerequisites merely to satisfy phase order. |
| P5 — Diagnose/integrate | A-027 reconciles case/variant coverage and completes the report and proposals. Publish the final evidence branch, explicitly integrate it into test main with two parents, verify/publish main, then retain the final checkpoint. An explicit earlier stop remains effective. |

A-003/API unavailable makes its dependent tracking claims Blocked. A local-only subset can continue eligible local scopes but is not full acceptance. Controlled local remotes/adapters exercise failure responses, not live GitHub success. Keep fixture actions, injected responses and consumer decisions distinguishable. Run installed-client observations only with an actual supported installation facility; record that gap independently of source-loading cases.

## Per-case procedure

1. Read the selected catalog entry and its exact consumer input, dependencies, assessor contract and trigger. Confirm prerequisite assessment and remote containment against live refs/objects. Snapshot starting product/evidence branch, HEAD/target/parents, task owners/status, dirty/index paths and relevant hosted identity. Exclude credentials/provider bodies from exports. Allocate `runs/<case-id>/<attempt>/`; append a new attempt after intervention/retry, never replace an earlier attempt.
2. Write RUN-STATE with current phase/case/attempt/role, last completed action, pending/uncertain operation, next action, checkpoint refs and evidence paths. For fresh handoff give only selected request/preparation requirements, pinned skill entries/references, applicable product instructions, actual current-state/authorization and tools. Record exact supplied input. Do not mount assessor expectations into the consumer context; if broad filesystem access makes them reachable, restrict the handoff/workspace or disclose the isolation limit.
3. Let the consumer perform the workflow through pinned skills and actual authorized tools. Retain sanitized actual journal/logs, executed commands/results, discovered task/branch/campaign/issue identities and final claim. When runtime native transcript is unavailable, distinguish structured observations from a complete transcript. Do not supply expected routing or silently drive Git/task lifecycle on its behalf.
4. At requested boundary/trigger, observe current state before continuation. A controlled interrupt must occur after the actual partial action is observed; save its state and launch a **separate fresh continuation**. If a required selected trigger cannot be observed, mark that variant Blocked; unavailable optional extensions are Not run/non-blocking. See [variant accounting](VARIANTS.md) and [trial controls](TRIAL-CONTROLS.md). Do not manufacture a claimed interruption by restoring a clean fixture. Follow [RECOVERY](RECOVERY.md) for staging, merge, archive and uncertain effects.
5. At the first consumer SDD commit, independently check [root disclosure and usage bootstrap](SETUP.md#consumer-repository-disclosure) from committed objects and pinned asset bytes; harness-created root copies do not demonstrate consumer behavior. Independent assessor receives contract, inputs, pinned source and sanitized durable actual evidence, not only consumer claims. Check literal API/CLI output/status/channels with expected constants, task ownership/scope, docs/errors/distribution, Git/index/merge parents/remote containment and relevant hosted owned/foreign fields. Run deterministic [assess](scripts/assess.py) where appropriate; assess agent behavior separately. Record expected versus observed and outcome/assistance.
6. If rejected, retain first attempt and assessment. Classify uncertainty before repair. Any clarification, coordinator correction, checker fix, restored facility or consumer retry gets an intervention record: exact reason, actor, scope, before/after evidence and objective recheck. Changes to input/checker are not invisible consumer success. Do not amend the pinned plugin; open a diagnostic proposal instead.
7. Update INPUTS only for resolved non-secret changes, RUN-STATE and RESUME via temporary-file replacement where supported. Update DIAGNOSTIC-REPORT progressively. Commit/push sanitized coordinator evidence to its reserved branch and verify remote containment **before dependent case execution**. Preserve product pending work without a completion commit. If evidence publication fails, record retained local refs/artifacts and pending push; don't claim the prerequisite is published.

## Stops and evidence ownership

Honor explicit `stop_after` after the selected phase/case assessment and preservation; record the reached boundary and publication status in RUN-STATE/RESUME and case evidence. It is a one-shot boundary. When a continuation is requested, reconcile actual evidence: a reached and recorded prior stop is consumed, then any pending checkpoint/publication is completed before continuing within the remaining previously authorized scope. An unreached or unverified stop remains active. If the authorized scope is exhausted, report completion and request new scope. Keep the original input/stop evidence and record consumption as a continuation action; do not rewrite the first attempt or silently broaden scope. A newly explicit stop in the current invocation remains active. Catalog mid-operation triggers interrupt before completion; record the precise observed trigger and fresh continuation boundary. A normal phase transition continues inside scope; a steering consumer stops after amendment, then the coordinator may issue the separately authorized next catalog request. Never interpret assessment-only as implementation authorization.

RUN-STATE is the coordinator's cursor, not product authority or a transaction guarantee. Retain `INPUTS.json`, `RUN-STATE.json`, `RESUME.md`, progressive `DIAGNOSTIC-REPORT.md`, and case directories containing input, journal/logs, assessment, interventions, Git/file/index exports. Distinguish local-only state from remotely recoverable bundles. The product's ordinary task/check evidence, commits and hosted links remain authoritative for its workflow. P5 reports missing facilities, unresolved effects and exact next action; the current invocation stops at its active boundary under the continuation rules above.

## Concrete selected assets and capture

Each entry resolves a unique consumer request, strict version 1 deterministic contract and independent assessor guide. Read [COMMON](cases/assessor/COMMON.md) and [INTERRUPTIONS](cases/assessor/INTERRUPTIONS.md) only in coordinator/assessor roles. The latter defines all controlled trigger/fresh-context pairs and native uncontrolled termination, including kill during an uncertain checkpoint/write/push/API effect. A missing runtime control facility is a coverage gap.

Run `python acceptance/textstats/cases/assessor/catalog_tools.py validate` from package root before dispatch; it checks actual asset/graph/contract integrity and explicitly does not certify runtime acceptance. Render selected consumer input with `catalog_tools.py render --case A-NNN --bindings RESOLVED.json --output NEW.md`. See COMMON for resolved checkpoint/assessment publication shape. Renderer verifies retained prerequisite objects and live destination containment; coordinator must independently establish assessment and exact current-state facts first. P0 initializes/publishes a bounded operating/harness baseline for initially empty repositories; A-001 has no completed product prerequisite. A-027 can report failed/blocked campaigns without a successful final product checkpoint.

Checkpoint bindings distinguish independently observed **starting** refs (especially A-002/A-011 no-action comparisons) from assessed **reached** refs. Never overwrite starting refs with final HEAD before a no-change comparison. Runtime task/feature/revision/hosted identities come from actual owners/observations. Consumer input receives selected ordinary product request/current-state only; all fault setup and desired decisions stay in assessor guides. Exact literal checks require actual capture.py output plus raw command provenance. Combine nonoverlapping suite literal keys into one version 1 evidence file without changing observations; retain each original capture/provenance. Use extracted package import root for distribution capture and retain actual packaging/extraction checks.

## Final evidence integration

After independent reconciliation and the final report/proposals are committed and published, integrate the reserved evidence branch into the established test `main` with `git merge --no-ff`. Retain the exact product-main tip and published evidence tip as ordered parents. Limit the merge delta to this campaign's evidence paths; preserve product files, unrelated evidence, immutable assessments and the tested-source pin. Resolve any evidence conflict within scope before committing; do not rewrite old attempts or turn unresolved required coverage into Passed. Reporting may complete with required Blocked outcomes, but required acceptance readiness remains false.

Inspect actual merge parents and evidence delta with [evidence_merge.py](scripts/evidence_merge.py) (`--root`, `--commit`, `--product-tip`, `--evidence-tip`, `--campaign-path` use retained full identities). Independently verify report links, assessment hashes and source manifest. Run relevant merged checks, normally push main, then read the exact remote main ref/containment. The helper does not verify publication or agent behavior. Preserve the original product-completion SHA separately from the later evidence integration SHA.

If main already contains the recorded evidence merge, verify its parents/content and remote state; do not merge again. If that merge is committed but unpublished, publish the retained merge after readback. Keep the evidence branch. An explicit pause, local-only or unmerged boundary overrides integration; report the pending final action and never claim full workflow completion. A post-merge checkpoint may record verified integration on main without making a second boundary merge.
